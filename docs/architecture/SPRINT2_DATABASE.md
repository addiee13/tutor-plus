`run-isolated.sh` creates a uniquely named `tutorplus_ddl_validation_*` database on the already running local Docker PostgreSQL server. ## Exact app and identity contracts

All application IDs are UUIDs. Role strings are **`student`, `tutor`, `administrator`**; do not use `admin` in application role rows. One account may have both Student and Tutor capabilities. `profiles.id` equals `auth.users.id`. Canonical columns are **`adult_attested boolean`** and **`status text`** (`active`/`inactive`), not the baseline proposal's `account_status`; the corresponding immutable `adult_attested_at timestamptz` is retained.

For managed signup, pass JSON boolean `adult_attested: true`, `display_name`, a PostgreSQL-known IANA `timezone`, and one initial intent via **`initial_role` or `role`**, limited to `student`/`tutor`. `initial_role` takes precedence; absent intent defaults to `student`. `role_intent` is not consumed. Administrator intent is rejected atomically. Signup attestation records a declaration, not verified age evidence. Missing attestation creates an ineligible profile; it is not repairable by ordinary self-edit. Managed Auth triggers provision profile, initial role and safe audit together; later metadata edits never create, alter or authorize capabilities. No password, token, or duplicate user store is created. Existing Auth accounts predating installation require an explicitly reviewed provisioning/backfill procedure, not a silent migration.

Own-profile self-edit columns: `display_name`, `bio`, `avatar_path`, `timezone`, `city`, `region`, `postal_code`, `country_code`, `learning_preferences`. `id`, eligibility, status, timestamps and role rows cannot be forged through a user-scoped write. PostgreSQL check constraints validate bounded strings, object-shaped preferences, timezone and code syntax; the application must also perform friendly field validation and validate avatar/storage ownership before displaying files. Currency/country checks enforce uppercase code syntax, not a full external ISO registry or provider-supported-currency catalog; USD is the local demonstration currency.

UI/server code must obtain a verified identity and use the **user-scoped access JWT**, not a service-role client, for ordinary profile/booking/role operations. Role RPC checks consult current database profile status and capabilities, not a JWT role claim beyond the provider access role. Generic user-visible authorization/conflict errors should not expose raw SQL constraint names or private row details.

### Non-sliding session boundary

`current_session_started_at()` is narrow `SECURITY DEFINER` with an empty pinned search path and schema-qualified object references. It parses the verified JWT `session_id` safely; missing/malformed UUID returns null. It joins session UUID **and** `auth.uid()`, requires `created_at <= statement_timestamp()`, rejects `created_at <= statement_timestamp() - interval '24 hours'`, and rejects an expired non-null provider `not_after`. Missing/revoked sessions return null. It returns only a timestamp, not provider session records. Cookie resets, access-token refresh, and a mutable `updated_at` cannot move the boundary. A fresh genuine login may legitimately create a new session and new start.

`private.active_actor()` additionally requires the current profile to be active, adult-attested and email-confirmed through managed Auth. Every private-table RLS policy and ordinary/admin mutation helper routes through this check. Public subjects/snapshots and public subject discovery intentionally remain publicly readable; public browsing is not a private authorization bypass. `statement_timestamp()` enforces the boundary per statement, not continuously inside an already running transaction. Direct database clients capable of forging JWT GUC settings are privileged test fixtures, not an untrusted browser; PostgREST/Auth must verify JWTs at ingress. Provider session policy configuration does not substitute for the authoritative join. Provider timebox is left unset locally; the requested 24-hour application boundary is enforced in SQL.

## Privacy, RLS and privileges

Every one of the 16 exposed domain tables has RLS and an explicit policy. Private control tables are in a non-exposed `private` schema and have no caller table grants. Private helper function execution is limited to the exact predicates needed by policies; other definer/trigger functions are not callable by ordinary clients. Function bodies use an empty search path; DDL resolves geography and exclusion opclasses through `extensions`.

| Resource | Ordinary permissions |
| --- | --- |
| `profiles` | Own verified eligible account: select and allowed-column updates only; no browser insertion/deletion |
| `user_roles` | Own rows; live administrators can inspect role rows; mutations only audited RPCs |
| `audit_logs` | Live administrators read; no caller mutations; append-only trigger also rejects privileged update/delete |
| `tutor_profiles` | Live Tutor: own source read, draft insert, allowed-column updates; immutable identity/version controlled by trigger; no delete |
| `tutor_subjects`, `availability_rules`, `availability_exceptions` | Live Tutor: own rows only; parent-tutor locking serializes scheduling changes |
| `subjects` | Public read of active catalog; catalog writes require separate reviewed operator/server work, not a browser grant |
| `public_tutor_snapshots` | Public read only when currently published/ready; no source/private profile join available to caller; caller mutations denied |
| `bookings`, `booking_private_details`, `booking_events` | Live participants read; booking mutations through RPC; event history append-only |
| `payments` | Live participants select only `id, booking_id, amount_minor, fee_minor, currency, state, paid_at, refunded_at, created_at, updated_at` |
| `refunds` | Live participants select only `id, payment_id, amount_minor, state, reason, created_at, updated_at` |
| `payment_events`, `payout_refs` | Explicit deny policy for ordinary authenticated access, no ordinary grants; provider identifiers/events remain private |

Financial `select('*')` fails deliberately because provider identifiers/idempotency keys are not granted; select the safe columns. Administrator capability does not grant blanket private learning/profile access. The service role cannot directly mutate profiles, roles, snapshots, financial tables, bookings or histories; use narrow RPCs. Its retained direct insert/update privilege on `booking_private_details` is only for a future trusted meeting adapter; no such app adapter is claimed here. It has read access required for privileged financial reconciliation; backend keys must remain server-only. Database-owner migration/operator access remains inherently privileged.

Tutor snapshots contain only explicit tutor-approved display, description, credential assertion, rate, modes, service-area and approximate-point fields. Credentials are self-described, not certified. Private display name, city/postal data, preferences, account state, user-role rows, meeting details and provider identifiers are not copied. Publication requires confirmed active adult Tutor, an active subject, an active non-expired recurrence rule and in-person location/radius readiness when needed. Public policies recheck current readiness, so revocation/inactivation/subject deactivation hides a previously built snapshot without a stale privilege window. Future geocoding must maintain approximate-location privacy; a geography type alone cannot prove that a coordinate is approximate.

## Booking and provider invariants

`private.booking_policy` holds **proposed local configuration**, not alleged course/client requirements: 60-minute lead, 365-day advance, 10-minute buffer on both ends, 15-minute payment hold, duration 15–180 minutes, zero platform-fee basis points. Operator-only changes require review; each reservation snapshots applied rate, buffer, hold and fee values. UTC `timestamptz` stores instants; `time`, weekday, local date, timezone and date bounds store local recurrence. Overnight recurrence must be split into two daily rules. DST uses PostgreSQL `AT TIME ZONE` resolution for rule endpoints; a polished future slot generator must explicitly handle repeated/nonexistent local wall times and show offset-bearing instants rather than ambiguous labels.

Reservation locks the scheduling tutor, then the student profile, rechecks subject/mode/eligibility/lead/duration/availability, expires relevant overdue holds, derives integer minor-unit price with ceiling on prorating, and inserts a pending hold. Rule/exception/subject edits lock the same parent tutor; an after-change check rejects availability edits that would invalidate an active reservation. Unavailable exceptions override additional intervals. A complete buffered interval must fit an allowed window. Two final GiST exclusion constraints reject overlapping `[)` blocking intervals for **both tutor and student**, in pending/confirmed/in-progress states; adjacent blocking intervals are permitted. Bookings and financial records use restrictive FKs, not cascading account deletion. Concurrent transactions are safe but may still report serialization/deadlock errors in more complex multi-tutor cleanup contention; retry the entire RPC with the same idempotency key, never partial manual writes.

Actor/subject/time/mode/price/currency/policy/request-key/hold-deadline snapshots cannot be updated, including privileged direct attempts. Rescheduling is deliberately **not** implemented as an unsafe update; a future reviewed transaction must replace a reservation atomically and handle money/history policy. Booking transitions are checked, versioned, and logged. Confirmation requires an authoritative paid payment. In-progress requires mode-appropriate private meeting details. Session lifecycle start/completion RPCs, notification emission and meeting adapters remain future work. Pending holds release lazily when another reservation touches relevant tutor/student; there is no claimed scheduler. Payment attempts independently reject expired holds. Retrying a booking key returns its original booking, including expired/cancelled state; callers must inspect that state rather than infer fresh availability.

Provider adapter contracts (all `service_role` only; empty-search-path definers):

| RPC | Signature / return |
| --- | --- |
| `prepare_booking_payment` | `(booking uuid, request_key text)` → payment uuid; canonical amount/fee/currency derived from the pending unexpired booking |
| `apply_verified_payment_event` | `(payment uuid, event_id text, requested_state text, occurred_at timestamptz, provider_payment_id text)` → boolean applied; states `requires_action/processing/paid/failed` |
| `reserve_refund` | `(payment uuid, request_key text, amount_minor bigint, reason text)` → refund uuid; pending/requested/successful totals cannot exceed capture |
| `apply_verified_refund_event` | `(refund uuid, event_id text, requested_state text, occurred_at timestamptz, provider_refund_id text)` → boolean applied; states `pending/succeeded/failed` |

These are **future signature-verified provider hooks, not a Stripe integration**. SQL cannot verify an HTTP webhook signature or prove an external charge/refund. A future server adapter must verify the provider signature against raw request bytes, validate event/payment/amount/currency identity, authorize booking ownership before preparation and persist actual provider references. Repeated provider event IDs are deduplicated and reject mismatched payment/type/time/refund identity. Older payment events and terminal paid/refunded states cannot regress. Refund terminal outcomes do not regress; the payment projection changes only after successful verified refund events. Payment and refund IDs/keys are unique; payment-row locking serializes refund reservation totals. A paid event arriving after hold expiry records paid money but cancels the booking with refund-review reason; a cancelled booking is never falsely confirmed. Operational reconciliation for cancelled-but-paid cases remains future work. No browser redirect, mocked client success or written test plan is payment evidence.
